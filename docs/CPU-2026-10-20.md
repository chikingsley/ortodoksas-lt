# CPU incident and release verification: October 20, 2026

## Cause and missed acceptance condition

The October 19 audit interval contained 1,274 Ortodoksas executions with Cloudflare's `exceededResources` status between 18:00 and 18:26 UTC. The subsequent Tiptap and query optimizations reduced rendering cost. The release review then accepted successful HTTP responses and successful execution outcomes while uncached rendering still exceeded Workers Free's 10ms CPU allowance. The October 20 baseline included uncached requests at 16ms, 25ms and 26ms. Cloudflare's occasional CPU headroom allowed successful responses above the documented limit. The earlier readiness conclusion therefore overstated the CPU evidence.

The October 19 crawl and presentation results remain historical evidence for their specific checks. CPU acceptance now additionally requires measured usage below the limit for the deployed version, with complete telemetry for the reviewed requests.

## Runtime correction

The public Worker handles revision lookup, edge caching and dispatch. Astro's supported custom entrypoint moves dynamic handling into `PublicationRenderer`, a SQLite-backed Durable Object class. Workers Free allows 30 seconds of CPU per Durable Object invocation. Eight named objects distribute rendering across a bounded set of instances. Their storage remains unused; content stays in the existing D1 database and media stays in R2. Static assets retain Cloudflare's asset-first delivery. The separate authenticated Studio keeps its existing deployment.

Public cache lifetime is 24 hours. Cache keys include the publication revision and deployed Worker version, so content edits, withdrawal, republication and deployment immediately select fresh content. OBL's key also includes the current date in Europe/Vilnius, keeping the default service month fresh across Lithuania's midnight boundary. Browser responses still require revalidation. Authenticated requests, API routes and private responses retain their existing cache bypass rules. Cache hits read one indexed revision row.

The account plan, custom domains and six existing bindings per site are preserved. The two added bindings are the renderer and Worker version metadata. The runtime uses the standard Cloudflare and Astro APIs and retains the existing lint and type strictness.

Sources: [Workers CPU limits](https://developers.cloudflare.com/workers/platform/limits/), [Durable Object limits](https://developers.cloudflare.com/durable-objects/platform/limits/), [Durable Object free allowances](https://developers.cloudflare.com/durable-objects/platform/pricing/) and [Astro custom entrypoints](https://docs.astro.build/en/guides/integrations-guide/cloudflare/).

## Required release evidence

Run `pnpm check`, deploy the intended main commit, then capture correlated Cloudflare tail events for both `stateless` and `durableObject` executions. Confirm that both streams are delivering events before starting the capture. Pace the representative route requests to retain complete evidence. Repeated requests must cover both `MISS` and `HIT` responses; include the large publication directories and each language edition. Tail sampling or missing events requires a fresh complete capture.

Normalize each request into `{id, cache, status}` and each execution into `{id, model, outcome, cpu, status, version}`. CPU values are milliseconds. Correlate the request and execution IDs using the `x-publication-review` request header. Preserve any capture failure in `summary.error`. The schema and examples live in `deployment/verify-cpu.mts` and `tests/publication-cpu.test.mts`.

Run `pnpm verify:cpu <report.json> <deployed-version-id>` against that capture. The command fails for CPU exhaustion, an unsuccessful outcome, a deployment mismatch, missing delivery evidence, missing cold-render evidence or absent cold/cache-hit coverage. Its regression tests run inside `pnpm check`.

Follow with the complete public sitemap crawl and a Cloudflare analytics check for resource failures during that deployment's interval. These checks establish separate HTTP, CPU and browser evidence. A successful HTTP response alone establishes delivery only.

Raw incident records, complete CPU captures, deployment readbacks, binding comparisons and crawl results are retained in the originating task's `cpu-alert` directory. The complete captures are `ortodoksas-canary-audit.json` and `obl-canary-audit.json`. The earlier partial telemetry capture is retained separately and fails the release gate.
